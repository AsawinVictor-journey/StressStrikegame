How the key actually travels

This is the part worth understanding, because it explains every rule below. The game never holds the key. It only knows the address of a small server you run, and that server is the only thing that talks to Google.

the whole chain
  Unity                      your server              Google
  GeminiClient.cs            server/.env
  ─────────────              ─────────────            ──────
  { model, prompt }   ───►   adds GEMINI_API_KEY ───► Gemini API
  (carries no key)           (the only place
                             the key exists)
        ◄───────────────  generated text  ◄──────────────

A Unity build is just files. Anyone with a copy can open them in a text editor and read every string inside — which is exactly why GeminiClient.cs has no key field, and why you should never add one.

The four steps

Order matters here: each step's check only means something once the one above it passes.

1

Put the key in server/.env

One file, one line. It lives at StressStrikegame\server\.env — outside Assets/, so Unity ignores it completely. It's already listed in .gitignore, so it can't be committed by accident.

server/.env — line 4
GEMINI_API_KEY=your key here

No quotes, no spaces around the =. Get a key free at aistudio.google.com/apikey.

2

Delete the stale Windows variable

This is the one still blocking you. A GEMINI_API_KEY is saved permanently in your Windows user account from an earlier experiment, and Node gives the environment priority over the file — so whatever you paste into .env is ignored while it exists.

powershell
> [Environment]::SetEnvironmentVariable('GEMINI_API_KEY', $null, 'User')
Then close and reopen your terminal

Environment changes never reach windows that are already open. If you skip this, nothing will appear to change and you'll assume the command failed.

3

Start the server

The most common mistake is running this from the wrong folder. --prefix server means “the folder called server, next to where I'm standing” — if you're in C:\Users\User, there isn't one.

powershell — two lines, run separately
> cd C:\Users\User\Documents\StressStrikegame\server
> npm start
Windows PowerShell has no &&

cd server && npm start is Bash syntax and throws a parser error here. Use two separate lines, or a semicolon: cd server; npm start.

Leave that window open while you play. Closing it doesn't break the game — the AI text just falls back to its written-in copy.

4

Verify — and don't trust /health alone

Open localhost:3000/health. You want gemini to read ready:

localhost:3000/health
{"ok":true,"gemini":"ready","cloudSync":"not configured"}

cloudSync: not configured is expected — that's MongoDB, which you're doing later.

This check can lie to you

ready only means a key was found. It does not mean the key is valid — that's exactly how the stale variable stayed hidden. The real test is asking the server to generate something:

powershell — the honest check
> Invoke-RestMethod -Method Post http://localhost:3000/api/gemini/generate `
    -ContentType 'application/json' `
    -Body '{"prompt":"Reply with exactly: HELLO"}'

text
----
HELLO

Get HELLO back and the whole chain works. Press Play in MainMenuScene and Coach Byte's text will start coming from Gemini.

When it breaks

Every one of these came up while setting this machine up — they're the errors you'll actually hit, not hypotheticals.

What you seeWhat it means
API key not valid The stale Windows variable is still winning over .env. Step 2, then reopen the terminal.
ENOENT … \server\package.json Wrong folder. You're in your home directory, not the project. Step 3.
The token '&&' is not a valid statement separator Bash syntax in PowerShell. Use two lines or a semicolon.
no longer available to new users A retired model ID. Already fixed everywhere — but if you add a new call, use gemini-3.5-flash-lite.
EADDRINUSE :3000 A server is already running. Find the old window and press Ctrl+C.
Text works, but reads generic The server isn't running, so the game used its fallback copy. That's by design — start the server.

Rules that keep the key safe

The first one is the whole reason the server exists.

  • ✕
    Never put the key in GeminiClient.cs, or any file under Assets/. It would compile into the build and be readable by anyone who has it.
  • ✕
    Never commit .env. It's gitignored — leave it that way.
  • ✕
    Never paste the key into a chat, an issue, or a screenshot.
  • ✓
    server/.env is the only place it belongs.
  • ✓
    Share it with teammates over a private message, and have them create their own .env. The same key works on every laptop — it isn't tied to a machine.

Later, not now

Two things deliberately left undone, so you're only debugging one system at a time.

Statistics board
Needs MongoDB Atlas. Uncomment the two lines at the bottom of .env and fill them in — no code changes. Until then /api/stats returns a clear 503 instead of crashing the server.
One shared server
Deploy server.js once and point every laptop at it with STRESSSTRIKE_API_BASE_URL. Then the key lives in one dashboard instead of on everyone's machine — worth doing before any demo on a borrowed laptop.
